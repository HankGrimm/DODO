# AI 匹配搭子（Monad 链）— Demo 阶段实现

对应 PRD `prd-ai-dazi-monad-2026-09-02.md` 第 9 节 **Demo 阶段**：跑通"发起匹配 → AI 撮合 → 组队押金 → 履约打卡 → SBT 铸造"最小闭环。

- 一套 Expo 代码同时出 Web 和 App（Web 先跑，后面直接 `npm run android` / `npm run ios`）
- 押金托管与履约凭证是 Monad 测试网上的真实合约，不是模拟
- AI 撮合走 OpenAI 兼容接口，没配 Key 时退回规则排序

## 目录

- `contracts/` — Solidity 合约 + 编译/部署/冒烟测试脚本（solc + viem，没上 Hardhat/Foundry）
  - `src/DaziEscrow.sol` 组队押金托管、双向打卡、举报、仲裁与罚没分账
  - `src/DaziSBT.sol` 不可转让履约凭证（ERC-5192 风格的 `locked()`）
- `app/` — Expo（SDK 57）应用，Web + iOS + Android 同一套代码

## 跑起来

**1. 部署合约**

```powershell
cd contracts
npm install
copy .env.example .env   # 填 DEPLOYER_PRIVATE_KEY，用一次性测试网账户
# 先去 https://faucet.monad.xyz 给这个地址领测试网 MON
npm run deploy
```

部署脚本会打印两行 `EXPO_PUBLIC_...` 地址。可选：`npm run smoke` 用两个真实账户在链上跑两个场景——完整闭环（断言押金退回、SBT 已铸造且不可转让），以及单方打卡后举报、仲裁罚没（断言罚没款按比例进安全基金、守约方净收益不足一整份押金）。

**2. 配置前端**

```powershell
cd ..\app
npm install
copy .env.example .env   # 贴入上一步的两个合约地址；要用大模型再填 LLM 三项
```

**3. 启动**

```powershell
npm run web        # 浏览器
npm run android    # 真机/模拟器（需 Android Studio）
npm run ios        # 需 macOS
```

## 演示路径（3-5 分钟）

1. 首页显示自动生成的链上账户与余额 —— 用户没有创建钱包、没有助记词、不需要懂 Gas
2. 去实名认证（未实名无法发起匹配，对应 R2）
3. 发起搭子：选场景（逛超市 / 同城出行）、地点、时间、押金额度、是否仅匹配同性别
4. AI 撮合返回候选人，卡片上给出信用分、守约/失约次数、距离和撮合依据；不满足硬性条件时明确提示"暂无匹配"，不凑数
5. 向候选人发出邀请 —— 这一步不动链，押金没被锁。对方同意后邀请才进入"待缴押金"
6. 组队 —— 链上两笔交易：本人 `createTeam` 押金入托管，搭子 `joinTeam` 押金入托管
7. 履约打卡 —— 获取定位 + 输入对方履约码，双方都确认后合约自动退还押金并给双方各铸一枚履约凭证
8. 信用页看到链上凭证列表与信用分三段式拆解（第三方征信一段明确标为未接入、不计分），以及本机黑名单

也可以在邀请页点"对方拒绝"，看到邀请作废且没有任何链上交易；或在组队页点"对方没来，我要举报"，看到组队进入"待仲裁"而不是直接扣款，并看到罚没条款——失约方罚 50%，其中一半赔给守约方、一半进安全基金。组队页还能拉黑对方，之后撮合不再推荐 TA。

## 哪些是真的，哪些是演的

真实的：合约逻辑、押金托管与退款、双向打卡校验（链上只存履约码哈希）、SBT 铸造与不可转让、罚没分账与安全基金累积、信用分计算（完全从链上记录算）。

Demo 简化，上线前必须替换：

- **对方账户是本机模拟的第二个内置钱包**。没有服务端和匹配池，所以"搭子"由 App 代为签名加入和打卡。邀请的同意/拒绝也是邀请页上的两个按钮手动触发的。真实产品里这些都发生在另一台设备上。
- **邀请状态只存在本地**（`dazi.invites`），链上不记录邀请，只记录最终成立的组队。所以状态机是单机的，没有双方一致性保证。
- **候选人池是本地种子数据**（`app/src/lib/candidates.ts`），不是实时请求池。
- **实名认证是本地模拟**：只校验格式并打标记，没接真实身份核验通道。
- **内置钱包是应用内托管私钥**，不是 ERC-4337 账户抽象。做到了"无感知"，但没有 Gas 代付和社交登录恢复。
- **没有摄像头扫码**：用 6 位履约码代替二维码扫描。
- **定位只做记录**，没有对约定地点做地理围栏校验（缺 POI 数据源）。
- **仲裁人是合约部署者**，`resolveDispute` 只落地资金与记录。谁来裁决、证据标准、误判申诉路径——PRD 待确认问题 4 还没答案，这里是占位实现。
- **安全基金只累积不支出**：罚没款留在托管合约里，没有提取函数。这笔钱谁能动、是用于线下安全核验还是误判补偿（PRD 待确认问题 3、4），还没有答案，所以刻意不写支出路径。
- **黑名单只在本机**（`dazi.blocked`），只影响自己看到的撮合结果，不上链也不改动对方信用分。PRD R3 里"被举报方复核期内不可发起新匹配"这半边需要服务端复核流程，没做。
- **双方都失约时不罚没**，各自退回押金，跟 `settleAfterDeadline`（双方都没打卡）保持一致。是否该对双方都罚一笔进安全基金，没定。
- **大模型 Key 通过 `EXPO_PUBLIC_` 注入，会被打包进前端代码**。只适合黑客松；正式环境必须由服务端代理。

## 刻意没做

按 PRD 第 8 节：不发可交易代币、不做"押注他人是否赴约"的盘口、不做公开信用分排行榜、不做拟人化情感陪伴（AI 提示词里明确约束为工具角色，禁止承诺人身安全）。

履约凭证只能证明"这个账号过去是否按时到场"，证明不了"这个人现实中是否安全"。这个信任悖论产品里靠文案反复说明，靠实名 + 举报 + 线下核验补，链上机制本身解决不了。
